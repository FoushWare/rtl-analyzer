# v0.6.3 security candidate: known limitations and deferred baseline defects

Candidate: implementation `a1e169c`, wrapper pin of the same commit (see the release report for the exact wrapper commit).

## Release gates (blocking)

- Canonical regression: `npm run test:e2e:regression` (apply and rollback, phase5 progress, security-negative, restart).
- Workflow lifecycle: `npm run test:e2e:workflow-lifecycle`; Node lifecycle: `npm run test:e2e:lifecycle-node`.
- Companion API lifecycle (authorization, Origin and approval gates, preview contracts): `RTL_REVIEW_SPECS=tests/e2e/api-companion-lifecycle.spec.ts`.
- Overlay security-hardening and rollback tests (`rtl:overlay:test`, `rtl:scan:test`), consumer packaging smoke (`rtl:cli:package:smoke`).
- Implementation-native checks (implementation CI `verify`): typecheck, build, unit, native E2E, runtime reuse, lint ratchet.

## Deferred pre-existing defects (diagnostic, non-blocking)

These fail identically at the published v0.6.2 baseline (`12c2c6d`). They are not security or source-integrity defects: no
rollback, authorization, or write path is reached before they fail.

1. **Review One-by-One preview startup.** The modified preview reports "did not start in time". Diagnostic job
   `review-diagnostics` (continue-on-error) keeps the journey visible.
2. **Apply First batch review.** The batch review's "View diff" action is not reached. Same diagnostic job.

The journeys' tests stay in the suite as diagnostic coverage. They are not marked as passing anywhere.

## Retired from required CI

- The implementation `e2e-default-debt` job (bare `playwright test` over every diagnostic spec) was red at v0.6.2. Its
  meaningful coverage is in the required native and overlay gates above. Unowned specs remain diagnostics and need an owner
  before they count as release coverage.

## Behavior noted, no security impact found

- v0.6.2's operation-dialog rollback calls the active workflow's rollback instead of naming an applied transaction id
  (`b03f490` in the working branch passes the id). The server validates the id, the receipts, and the confirmation on
  every request, so a wrong target is refused. Not included in this candidate.

## Coverage gaps

- Receipt tampering is covered for the trusted-receipt fields (applied and original hashes, audit id, path, backup path).
  No test covers a backup whose bytes are changed after apply (the restore path checks the backup hash and refuses).
