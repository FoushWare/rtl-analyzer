# Review-mode entry and restoration

Verified 2026-11-21 (Africa/Cairo). CONTINUE of the approved dashboard task; human acceptance remains pending. No new project, transformation mode, push, publication, deployment or worktree cleanup.

## Diagnosis

The chooser was present. The client initially bypassed it when `localStorage['rtl-review-workflow']` held a mode, then looked up the companion's persisted review for that mode. If that lookup found no review, it reopened the chooser. The preference is not itself proof of an active review.

Read-only inspection of Ahmed's existing in-app browser tab found an older loaded document: **Change review workflow**, **Current review · One by one**, and the old **1 of 6** counter. That tab was running an old page and displaying an existing one-by-one review. The source and fresh browser tests confirm that restoring a saved preference/session bypasses the chooser; the accessibility snapshot alone cannot establish how that older tab originally entered its review. It was left untouched so any in-memory drafts in the older code were not lost. Fresh installed-package browser checks use the current artifact and actual companion.

## Scoped changes

- The visible header action is now **Change review mode**. **Review actions → Start new review** remains discoverable.
- A restored review says **Restored review · One by one** or **Restored review · Prepare all, then review**. Fresh entry says Current review. The mode comes from the persisted workflow, not inferred from preview state.
- With no active review, the existing chooser presents exactly the two supported modes with concise explanations and a clear no-active-session message. A stale browser preference also returns to that chooser.
- Reopening the chooser shows the current mode, explains that switching restores that mode's saved review when available (otherwise starts it), and explains that decisions/drafts stay with their review. **Return to current review** cancels the chooser without changing mode or state.
- The chooser explicitly says preparation happens in an isolated candidate and original files change only through the separate explicit Apply step.
- Drafts retain their existing in-memory map and are additionally saved in browser-tab `sessionStorage`, namespaced by report identity and review/finding IDs. Mode switches and reload retain the correct review's draft; drafts do not become persisted decisions or silently overwrite saved notes. Save/Cancel explicitly remove that draft. This does not import hidden drafts from an already-loaded older dashboard; its tab remains untouched.
- Changing modes uses existing per-mode review restoration/creation. It does not restart an existing review, clear its decisions, or call source Apply. No source identity, approval, validation, Apply or rollback safeguard changed.
